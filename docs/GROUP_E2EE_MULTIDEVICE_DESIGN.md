# Group E2EE: multi-device Sender Key design (v2)

Status: implemented on branch `fix/group-e2ee-hardening` (not merged). There is
exactly ONE wire format (v2). The system has no users yet, so there is no legacy
path, no migration and no compatibility shim: v1 KDMs, the `scheme` field, the old
id derivation, account-wide `delivered_at` delivery and "no `device_id`" requests
were removed, not deprecated.

Tests: `tests/groups/` (run `npm test`). MD-1..MD-6 (`group-multidevice`), audit
cases F-I/G (`group-audit`), L-1 (`group-keys-contract`), and one file per hardening
finding: `group-hardening-f1-crash`, `-wire` (F2/F3/F8/F10), `-f10-rollback`,
`-f4-replay`, `-f5-removal-race`, `-f6-device-id`, `-f7-version-gate`,
`-f9-web-locks`, `-f12-credentials`.

## 1. What this protects, and what it cannot

Protects: group message and attachment confidentiality and integrity against the
server operator and against anyone who obtains the database, as long as the web
client code the user runs is honest.

**It cannot protect against a malicious server delivering malicious JavaScript.**
The web client is loaded from the same server it talks to, so a hostile or
compromised server can ship code that exfiltrates the password or the keys. This is
inherent to web E2EE. It is only mitigated, not solved, by installed
Capacitor/Electron builds (their assets are fixed until the user updates) and by the
service worker (which pins a manifest, but is itself served by the server on first
load). Do not describe this system as "the server cannot read your messages" without
this caveat.

Also true by design: a malicious server can still drop messages, reorder them,
withhold KDMs, and learn who talks in which group and when.

## 2. Protocol v2

### 2.1 Credentials (F12): the password never reaches the server

```
master  = PBKDF2-HMAC-SHA-256(password, accountSalt, 600,000 iterations)   32 bytes
authKey = HKDF-SHA-256(master, salt = 32 zero bytes, info = "Wire-Auth-v1")
wrapKey = HKDF-SHA-256(master, salt = 32 zero bytes, info = "Wire-Identity-Wrap-v1")
```

* `authKey` (43 base64url chars) is the only secret-derived value sent to the server
  (login, registration, password change, "confirm your password" prompts). The server
  stores `bcrypt(authKey)`. It cannot derive `wrapKey` or `master` from it
  (independent HKDF outputs).
* `wrapKey` AES-256-GCM-encrypts the X25519 identity private key (PKCS#8). It never
  leaves the browser. The "remember me" cache stores exactly these 32 bytes on the
  device; whoever has them can decrypt the identity.
* `accountSalt` (16 random bytes, generated by the client at registration, fresh on
  every password change) and the iteration count live in
  `users.kdf_salt/kdf_iterations`. They are public: `GET /api/auth/kdf-params?username=`
  serves them before login; unknown usernames get a deterministic fake salt (HMAC of
  the username under a server secret) so the endpoint does not reveal which accounts
  exist. `GET /api/me/kdf-params` returns the caller's own.
* Floors: the server rejects `kdf_iterations < 600000`, an identity whose KDF is not
  `PBKDF2-SHA-256+HKDF-SHA-256`, version != 2, or a salt/iterations different from the
  account's. The **client** also refuses any KDF parameters below 600,000 whatever the
  server answers (a hostile server asking for 1 iteration would otherwise harvest a
  trivially brute-forceable `authKey`).
* Every endpoint rejects bodies that still carry `password`, `current_password` or
  `new_password` (HTTP 400, `raw_password_rejected`).
* Password change: the browser derives old and new credentials, decrypts the identity
  with the old `wrapKey`, re-encrypts it with the new one under a new salt, and sends
  `{current_auth_key, new_auth_key, new_kdf_salt, new_kdf_iterations, identity}`; the
  server swaps all of it in one transaction. The X25519 identity (and therefore every
  group key wrapped to it) does not change. (Before this branch the re-wrap tried to
  export a non-extractable key and failed whenever an identity existed.)
* Registration, login and password change run a 600k-iteration PBKDF2 in the browser
  (a few hundred ms on a desktop, noticeably more on a low-end phone). Login derives
  twice (authKey for login, wrapKey again at identity unlock); a shared cache would
  halve that and was left out to keep the derivation stateless.

**There is no password reset.** The password protects the identity key and the server
cannot decrypt it. Forgetting the password loses the identity: encrypted history
becomes unreadable, and a "reset" can only create a new, empty identity. The
registration screen says so. See section 6 for an optional recovery key (decision
pending). The codebase has no password-reset route, so nothing had to be removed there.

Operator-supplied passwords: the first-run setup wizard and `DEFAULT_ADMIN_PASS` derive
`authKey` locally with the same algorithm (`utils/credentials.js`, verified
byte-identical to the browser module by a test), but the plaintext password is, by
definition, seen by the process on the host where the operator types it. An admin
creating a user from the UI also knows the password they typed. Both should be changed
by the account owner at first login.

### 2.2 Sender Key and its id (F8)

A Sender Key is a random 32-byte **root** secret. It is never used directly:

```
encKey = HKDF-SHA-256(root, salt = 32 zero bytes, info = "Wire-GroupKey-enc-v2")  -> AES-256-GCM
idKey  = HKDF-SHA-256(root, salt = 32 zero bytes, info = "Wire-GroupKey-id-v2")   -> HMAC-SHA-256
senderKeyId = hex(HMAC-SHA-256(idKey, encodeFields("group-sender-key-id-v2", groupId, ownerUserId, epoch)))
```

The id is a PRF of the key: two devices of one account minting at the same epoch get
different ids; recipients derive the id after unwrapping the KDM (nothing extra is
transmitted); publishing the id reveals nothing about `encKey`. `encodeFields` is the
unambiguous encoding used everywhere below: each field is written as type (1 byte),
length (4 bytes, big-endian), then the bytes, so there is no "|"-join ambiguity.

### 2.3 Message envelope and nonce (F3, F10)

`{v:2, alg:"AES-GCM", senderKeyId, counter, iv, ciphertext}`

* `iv` (12 bytes) = `prefix(4) || counter(8, big-endian)`.
* `prefix` is **random per JS process and redrawn on every identity lock/unlock**. It
  lives only in memory and is NOT stored with the key. A restored or cloned profile has
  the same key and possibly an older counter; a stored prefix would reproduce the same
  nonces, a fresh one does not. Residual risk: two processes that reuse the same counter
  value collide with probability 2^-32 per pair. The counter is still persisted,
  reserved-then-used under a Web Lock, so one profile never repeats a counter.
* AAD = `encodeFields("group-msg-v2", groupId, senderKeyId, counter, iv)`; attachments
  use the label `"group-att-v2"` and the same counter/nonce space.
* The receiver does not know the prefix. It requires `iv.length == 12` and that the last
  8 bytes of `iv` equal `envelope.counter`, then decrypts with the AAD above. So the
  counter, the group, the key id and the iv cannot be relabelled.

### 2.4 Key distribution message, KDM v2 (F2)

`group_key_distributions.wrapped_key` = `{v:2, alg:"AES-GCM", iv, ciphertext}` wrapping
the 32-byte root for one recipient.

* Wrap key = HKDF over the same X25519 ECDH as 1:1 DMs but with info
  `Wire-E2EE-Group-KDM-v2` (DMs use `Wire-E2EE-v1`), so a DM ciphertext can never be
  accepted as a KDM or the reverse.
* AAD = `encodeFields("group-kdm-v2", groupId, fromUserId, toUserId, epoch, 2)`, taken
  from the server row on receipt. A relabelled row (other group, epoch, recipient or
  sender) fails authentication. `senderKeyId` is not in the AAD (it is derived from the
  key after unwrapping).
* Only `v:2` exists. Anything else is rejected and, crucially, **not acked**.

### 2.5 Replay protection (F4)

Each device keeps a seen-set in IndexedDB (`seen-counters`): one row per
`(senderKeyId, full 12-byte nonce)` it has accepted, bound to the **server message id**
(or attachment reference) that first claimed it.

* The claim is made only **after** AES-GCM authentication succeeds, in one IndexedDB
  transaction (get + put), so a corrupt message never burns a nonce and two tabs racing
  on the same database are serialised: exactly one of two competing ids wins.
* Same id again (socket + `syncSince` after a reconnect, reload, quoted reply preview,
  another tab): accepted, idempotent, never shown as an error. Same nonce under a
  different id: `ReplayedMessageError`, the message is dropped.
* The set is keyed by the full nonce, not the counter alone: after a counter rollback
  (F10) fresh messages legitimately reuse old counter values under a new prefix and must
  not look like replays.
* Out-of-order delivery is fine (a set, not a high-water mark). Attachments and messages
  share it.
* Cleanup: rows are deleted with their key (group left/removed, forgotten key). They are
  kept across rotation (the old key still decrypts history, so it must keep rejecting
  replays). A cap of 100,000 rows per key evicts the oldest ~10%; eviction only ever
  weakens protection for ancient messages, it never rejects a legitimate one.
* The decrypt API requires the message id; there is no unprotected path.
* Limits: the seen-set is per device; the server can still replay to a device that has
  no row (new device, wiped storage) before the original arrives. Dropping and
  reordering by the server are not detected.

### 2.6 Mailbox, devices, receipts (F6)

* A KDM is delivered to a **device**: `group_kdm_receipts(kdm_id, device_id)`. A device
  acks only KDMs it stored, so a second device still receives keys the first one already
  consumed (MD-4). `device_id` is mandatory on drain and ack (400 otherwise).
* The client generates `device_id` once per browser profile and stores it in the same
  IndexedDB as its keys (if the keys are wiped, the id goes with them and the server
  re-delivers everything).
* Server: `group_devices(user_id, device_id, ...)` registry. Cap 20 ids per user (least
  recently seen evicted together with its receipts). Creating new ids is throttled
  (429 + `Retry-After`, default 20/hour) **only once the account has 5 devices**; ids
  the account already knows are never throttled. Tabs of one profile share one id.
  Devices unseen for 90 days and orphan receipts are pruned every 6 hours; receipts
  cascade with their KDM row. Env: `GROUP_DEVICE_CAP`, `GROUP_DEVICE_NEW_PER_HOUR`,
  `GROUP_DEVICE_GRACE`, `GROUP_DEVICE_TTL_DAYS`.
* `device_id` is a cursor, not a credential: knowing someone's id lets an authenticated
  user re-download only their own mailbox.

### 2.7 Sending keys and crash safety (F1, F9)

* Sending keys are device-local: a key is a sending key only if this device generated it
  (`isMine == 1`). Received keys, including self-KDMs from another device of the same
  account, are decrypt-only and never demote an existing sending key (atomic
  insert-if-absent).
* **MD-6 closed on crash:** a new sending key is held in memory only and written to
  IndexedDB after the KDM POST returned 201. If the process dies before or during the
  POST nothing is on disk and the next call mints and distributes a fresh key. If it dies
  after the server stored the KDMs but before the write, recipients hold a key this device
  lost and it mints another (harmless: ids are per key, nonces per key).
* Sending requires `navigator.locks` (nonce counters); without it sending throws. Key
  minting falls back to unlocked, which can only produce an extra key, never a nonce
  reuse. On Capacitor WebViews: Android WebView (Chromium) supports Web Locks in secure
  contexts; iOS WKWebView supports them from 15.4. Whether the Capacitor origin counts as
  a secure context on each target was NOT verified on a device: check `navigator.locks`
  there. If it is missing, those clients can read but cannot send.

### 2.8 Server rules (F5, F7)

* `POST /api/groups/:id/kdms` validates, in the same transaction as the insert: the
  sender is a member, `epoch` equals the sender's current `key_epoch` (stale -> 409), and
  every recipient is a current member. All-or-nothing. Removal purges the removed
  member's KDMs and evicts their sockets from `group:<id>`; drain only serves groups the
  caller is in.
* Version gate: the client sends `X-Wire-Group-Proto: 2`; KDM and message endpoints
  answer anything older or missing with HTTP 426 and `{code:"update_required", min_group_protocol:2}`,
  and the client shows a toast. Group management stays reachable.
  A client that cannot parse a KDM never acks it, so the server keeps it for after the
  update (locked in by a test).

## 3. Why this exists (reproduced with the real server, Socket.IO and client)

1. Two devices of one account used to mint the same key id for different keys, so a
   recipient overwrote one with the other (MD-2) and both devices could encrypt under one
   key with independent counters from 0: (key, nonce) reuse (MD-3 recovers
   `c1 XOR c2 == p1 XOR p2` from the DB).
2. The mailbox was consumed once per account, so a later device never got keys another
   device had drained (MD-4).
3. A failed or interrupted KDM POST left an undistributed key as current (MD-6); two tabs
   both minting a first key (MD-5).

## 4. Capacity

Every connected device of a member mints its own key at each membership change, and
adding a member also bumps the epoch, so a rotation writes about `members x devices` KDM
rows per sender. At 50 members x 3 devices that is thousands of rows per event. Set a
group-size cap before allowing large groups.

## 5. Known limits (out of scope here)

* One X25519 identity per account, restored on every device: no forward secrecy on key
  distribution (a stolen password plus the server's wrapped identity decrypts every group
  key ever sent to that user), one browser cannot be revoked (rotate the account
  identity), KDMs are unsigned (unwrap success is the only authenticity).
* No per-message sender authentication: any member holding a sender's key can encrypt
  under it; attribution relies on the server's `sender_id`. This is Megolm with a portable
  identity, not Signal Sender Keys with device identities.
* PBKDF2 is not memory-hard. A database leak costs an attacker 600,000 SHA-256 iterations
  per guess; a memory-hard KDF (Argon2id via WASM) would be stronger.
* No history backfill for a newly added member (by design).
* The malicious-JavaScript limit in section 1.

Two bullets above are superseded by section 7 (Phase C, per-message sender
authentication): "No per-message sender authentication" and the claim that KDMs
are unsigned.

Next protocol bump: device identity keys, signed KDMs, wrap per recipient device (then one
laptop can be revoked). MLS only if groups grow past a few dozen people.

## 6. Open decision: optional recovery key

Not implemented. Sketch, for the owner to accept or reject: at registration the client
generates a 256-bit recovery key shown once (and offered as a file/QR), and uploads a
second copy of the identity encrypted under
`HKDF(recoveryKey, "Wire-Identity-Recovery-v1")`. Reset-with-recovery-key then keeps the
identity and history; without it a reset still means a new identity. Cost: one more secret
users must store, and a carelessly stored recovery key is a second way to the identity.
Default recommendation: leave it out for a small private server and keep the "no
recovery" statement.

## 7. Per-message sender authentication (Phase C)

Status: implemented in Phase C (sub-steps C1 to C4), tests listed in 7.9. This section
supersedes the first bullet of section 5 ("No per-message sender authentication") and the
bullet about KDM rows without AAD (the KDM has been AAD-bound since F2, see 7.2).

**Wire format change.** The group protocol version is still `v:2`. It was **changed in place**:
the group protocol is unreleased, there is no v3 and no compatibility layer. Test groups created
before Phase C must be **recreated** (see 7.8).

### 7.1 What it adds

AES-GCM under a Sender Key is symmetric: every member who holds Alice's Sender Key can produce
a ciphertext that authenticates as "Alice's key". Phase C gives every Sender Key its own **ECDSA
P-256 / SHA-256 signing key pair** (WebCrypto only). Every group message is signed with the private
key of the Sender Key it is encrypted under; a receiver accepts a message only if the signature
verifies under the public key that arrived in a KDM unwrapped under the pairwise key of the claimed
sender. A message is attributed to the **owner of the verified key**, never to the server's `sender_id`.
Nothing about the account-level identity model changes. Each device has its own Sender Key and
therefore its own signing key; nothing signing-related is shared between devices.

### 7.2 Wire format

**Message envelope** (JSON string stored in `group_messages.content`; the server treats it as opaque):

| Field | Value |
|---|---|
| `v` | `2` |
| `alg` | `"AES-GCM"` |
| `senderKeyId` | 64 lowercase hex characters (see "Sender Key id" below) |
| `counter` | non-negative integer; must equal the last 8 bytes of the nonce |
| `iv` | base64 of the 12-byte nonce: 4-byte random per-process prefix, then the 8-byte big-endian counter |
| `ciphertext` | base64 of the AES-256-GCM output (ciphertext and 16-byte tag) |
| `reply_to_id` | **new**: positive integer or `null`; signed |
| `sig` | **new**: base64 of the raw 64-byte IEEE P1363 ECDSA signature (r then s) |

Any envelope key named `att`, `attachment` or `attachments` is refused (unverified): group attachments
are disabled and their bytes are not bound into the signature (see 7.7, item 5).

**AES-GCM additional data of a message**: `encodeFields("group-msg-v2", groupId, senderKeyId, counter, iv)`.

**`encodeFields`** (`public/js/crypto/groups/codec.js`): every field is written as
`1 type byte (0 = UTF-8 text, 1 = raw bytes) | 4-byte big-endian length | data`; numbers are their decimal text.
No two different field lists encode to the same bytes (property-tested in `group-signing.test.mjs`).

**Signed bytes** (`public/js/crypto/groups/signing.js`, `encodeSignedBytes`), in this order:

| # | Field | Encoding |
|---|---|---|
| 1 | label | text `"wire-group-msg-sig/v1"` (domain separation) |
| 2 | `groupId` | decimal text (the group the message ARRIVED in) |
| 3 | `senderKeyId` | text |
| 4 | `counter` | decimal text |
| 5 | `iv` | raw bytes, exactly 12 |
| 6 | `ciphertext` | raw bytes, **decoded** (never the base64 text, which is not canonical) |
| 7 | `reply_to_id` | decimal text, or a raw empty field for `null` (the two cannot collide) |
| 8 | attachment slot | raw bytes, **empty today** (reserved) |

The signature is over the ciphertext (encrypt, then sign) so it is verified **before** anything is decrypted.
ECDSA signatures are malleable (`(r, n-s)` also verifies; no low-S rule). That cannot create a second accepted
message because acceptance is keyed by `(senderKeyId, full 12-byte nonce)` in the seen-set (tested in
`group-signing.test.mjs`).

**KDM** (`group_key_distributions.wrapped_key`): JSON `{v:2, alg:"AES-GCM", iv, ciphertext}`.
The **plaintext is 97 bytes**: the 32-byte root key, then the 65-byte raw uncompressed signing public key
(`0x04 || X || Y`), wrapped under the pairwise DM session key.
AES-GCM additional data: `encodeFields("group-kdm-v2", groupId, fromUserId, toUserId, epoch, 2)`; the public key sits inside the
authenticated plaintext, so the GCM tag covers it. Any other plaintext length (a 32-byte plaintext is the
pre-signing format), a first point byte other than `0x04`, or a point that is not on the curve is rejected
(`KdmFormatError`; `LegacyKdmError` for the old format) before anything is stored.

**Sender Key id** (`sender-key-id.js`): `encKey = HKDF(root, "Wire-GroupKey-enc-v2")`,
`idKey = HKDF(root, "Wire-GroupKey-id-v2")`, and
`senderKeyId = hex(HMAC-SHA-256(idKey, encodeFields("group-sender-key-id-v2", groupId, ownerUserId, epoch, signPub)))`.
The id **commits to `signPub`**: the message AAD and the signed bytes both carry the id, so ciphertext and signature
are bound to this exact key pair; a second KDM with the same root and another signing key gets another id and can
never alias or overwrite an existing key; and a stored row whose `signPub`, owner, epoch or group was altered no longer
re-derives to its own id (checked on every load; the row is then unusable and its messages stay unverified).

**Local storage** (IndexedDB `wire-group-crypto`, store `sender-keys`, one record per key): the existing fields plus
`signPub` (base64, 65 bytes, every row) and, **only on keys generated on this device**, `signKeyWrapped {iv, ciphertext}`:
the PKCS#8 signing private key (138 bytes) under the local wrap key with additional data
`encodeFields("group-sig-priv-v1", senderKeyId, ownerUserId)`, written in the **same put** as the root, after the
KDM POST returned 201. A received key never has a signing private key.

### 7.3 Key lifecycle

* **Generation.** The private key is generated extractable only to be exported once (PKCS#8) and wrapped; the key
  used afterwards is a **non-extractable** re-import; every temporary buffer is zeroed (KDM plaintexts too).
* **Receipt.** `receiveKdm` unwraps under the pairwise key of the row's `from_user_id`, validates the structure,
  derives the id from `(group, from_user_id, epoch, root, signPub)` and only then stores. The **owner is the sender
  proven by the unwrap**, never a field the server can relabel. The owner, group, epoch and `signPub` of a stored id are
  immutable (`SenderKeyConflictError`).
* **Rotation.** A new Sender Key means a new pair. The superseded **own private signing key** is dropped only after the new
  key is durably stored, after the KDM POST returned 201, under the same sender-key lock; the old row keeps its root and
  public key so its history still decrypts and verifies. A failed or crashed rotation leaves the old key usable; a send that
  already holds the old signing key still signs. Non-deferred generation never drops anything; the next successful rotation
  does.
* **Sending** requires an own row (`isMine`) with a signing key that matches its public key. A row without one (a
  pre-signing row) is unusable for sending and the next ensure re-keys.
* **Second device.** It stores the other device's root and `signPub` verify-only and never obtains a private signing key.
* **Lock / logout.** `lockIdentity` clears every cached key, the signing keys included.

### 7.4 Receive order (`groups/message-crypto.js`, `decryptGroupMessageDetailed`)

1. Parse the envelope; check version, `senderKeyId`, counter and nonce shape (a malformed envelope throws a plain error and is
   dropped per message).
2. Refuse unexpected attachment fields; require a 64-byte `sig` and a `reply_to_id` that is `null` or a positive integer.
3. Load the key. No row: "waiting for key" (the only retried state). A row that cannot verify (no `signPub`, invalid
   key, id mismatch): **permanently unverified**.
4. **Verify the signature** (this is before decrypting and before claiming the nonce).
5. The verified owner must equal the server's `sender_id`; the signed `reply_to_id` is authoritative: a non-null server value
   that differs is a swap, a null server value with a signed target is allowed (deleted, or in another group where the server drops it).
   Both checks run **before** the claim so a re-post cannot burn the genuine message's nonce.
6. AES-GCM decrypt (additional data above).
7. Claim `(senderKeyId, nonce)` in the seen-set (`new`, `same` for the same message id, or `conflict`).

The client then builds the reply quote from the **signed** id, only from a server row that really is that message
(otherwise "Original message deleted"); the quoted message is verified like any message and its verified owner must equal the
user the server names as its author.

### 7.5 What the user sees

* Unverified message: nothing from it is rendered. A static placeholder (`⚠️ Message could not be verified`, built only from
  a CSS class, no interpolated data). It is **permanent**: never retried after a KDM drain or reconnect. Bulk history shows it
  in place (ids and order kept); a history fetch logs one aggregated console line.
* Unverified quote: the static label `⚠️ Unverified message`.
* Key not arrived: unchanged, `🔒 Waiting for encryption key…`, retried after a KDM drain.

### 7.6 Threat model

**The signature prevents:**

* a member who holds another member's Sender Key forging messages as that member (the forger cannot sign as the owner);
* the server relabelling the author of a message (`sender_id` is checked against the verified key's owner; a member re-posting
  someone else's signed message as his own is refused);
* key substitution in transit: the signing public key travels inside the AEAD of the KDM, bound to group, sender, recipient and
  epoch, and committed by the key id, so the server and third members cannot swap it; ownership follows the pairwise unwrap;
* cross-group replay of a valid envelope (the group id and the key id are signed);
* reply-target swaps (the target is signed; the server may only agree or drop it).

**It does NOT prevent or protect:**

* metadata: who talks to whom, when, message sizes, the membership list, timestamps, message ids and ordering (all server-controlled);
* deletion or omission: the server can delete messages or withhold them; a thread can be rewritten by omission (no history
  integrity, no gap detection);
* reactions, edits of server-side columns, and every other server column (they are not signed);
* availability: the server can refuse service or drop KDMs;
* confidentiality changes: Sender Keys still give no post-compromise security and no per-message forward secrecy; the signature adds
  authentication, not secrecy;
* identity-key attacks (see 7.7).

### 7.7 Known limitations

1. **Replay window at seen-set eviction.** After the soft cap evicted a nonce (about 90,000 messages by one key), a hostile
   **server** that re-posts the stored message under the **original** `sender_id` is accepted once; the same replay by a **member**
   under his own `sender_id` is rejected because the verified owner differs. Pinned by **C4-2**
   (`tests/groups/group-signing-adversarial.test.mjs`, named "KNOWN, ACCEPTED LIMITATION"). Scheduled rotation (8.1) would make
   the window unreachable.
2. **No epoch or membership cut-off on receive.** The client accepts any known key id whatever its epoch, so a message validly signed by a
   **removed member's own old key** is attributed to **her** (never to anyone else, never as a member's message). The server is the
   membership gate. A message signed late by a superseded key whose signing handle was still in memory (an in-flight send) is
   accepted. Pinned by **C4-5** and **C4-7** (same file); proposal in 8.2.
3. **No identity pinning, no fingerprints.** `keys/peer-keys.js` fetches peer identity public keys from the server with no pinning
   or safety number. A malicious server can still substitute identity public keys (and so read and forge at the account level);
   the signatures do not change that. Proposal in 8.4.
4. **Leaked passwords leak the identity.** The identity key is wrapped under the password-derived key and stored server-side
   (login scheme 2); anyone with the password and the wrapped blob recovers the identity and can then act as the account. Accepted.
5. **Group attachments are disabled and must bind their bytes into the signature before they are ever enabled.** The envelope
   has a reserved, empty attachment slot in the signed bytes; an envelope carrying attachment fields is refused; the attachment
   bytes themselves are only AEAD-protected under the Sender Key, so any member could forge a file "from" the key's owner. Pinned
   by **C3-12** (`tests/groups/group-signing-messages.test.mjs`), which fails if any client module starts calling
   `encryptAttachmentForGroup` and says what must be done first.
6. **A hostile role through a hostile members API is not covered.** The real-Chromium test
   (`tests/groups/group-hostile-browser.test.mjs`) edits the database, where `group_members.role` is schema-constrained to
   `owner`/`admin`/`member`, so a hostile role cannot be stored and was not exercised; a server that answers the members API
   with a hostile role is not covered.
7. Also by design: a structurally **malformed** envelope is dropped per message (nothing rendered, existing contract
   `K-2` in `group-keys-contract.test.mjs`); only a well-formed envelope that fails verification gets the placeholder. The bulk fetch
   omits "waiting for key" messages, as before.

### 7.8 Compatibility and migration

v2 changed in place and is unreleased: **there is no migration code; test groups created before Phase C must be recreated.**
What happens to old data, so nothing is surprising:

* Old messages have no `sig`: unverified placeholders.
* Old KDMs (32-byte plaintext) are never consumed and **never acked**; a drain logs **one** console line summarising them.
* A received row without `signPub` is kept but unusable: its messages are permanently unverified (not an endless "waiting for key"),
  one console line per key id per session.
* An own row without a signing key is unusable for sending; the next send re-keys.
* The server is unchanged and opaque to the new fields (`wrapped_key` and `content` are opaque strings).

## 8. Proposals (NOT implemented)

### 8.1 Scheduled Sender Key rotation

**What.** A device re-keys its own Sender Key (same epoch) when it has sent N messages with it **or** the key is a few days old,
whichever comes first: checked at send time inside the existing ensure lock (the same path as today's re-key; selection of the live
key by `(epoch, createdAt)` and the "drop the superseded private signing key after the 201" rule already exist).
Suggested start: N = 1,000 and 7 days.

**Why.** (a) It bounds the exposure of one leaked device key. (b) It bounds every key's seen-set to N rows, so with N well below the
90,000-row soft cap the eviction window of 7.7 item 1 becomes unreachable. (c) It bounds counters and the work of a "catch up" sync.

**Cost** (estimates from the sizes in 7.2 and Node timings of the primitives: sign 0.10 ms, verify 0.19 ms, public-key import 0.09 ms;
not measured on a phone):

| Item | One rotation by one device, 20 members | A membership change today, 20 members x 3 devices |
|---|---|---|
| KDM rows posted | 20 (one per member account) | 60 devices x 20 = 1,200 |
| Size of one `wrapped_key` | about 215 bytes of JSON (97 + 16 tag = 113 bytes, 152 base64 chars) | same |
| Posted bytes | about 4.3 KB | about 260 KB |
| Rows read per recipient device | 1 | 60 (one per sender device) |
| Client work per received KDM | one unwrap, HKDF, id derivation, public-key import: well under a millisecond on a desktop | x 60 |

A scheduled rotation is therefore two orders of magnitude cheaper than a membership change; the first send after it waits one
round trip (the KDM POST). **Risks:** more mailbox rows and receipts to prune; a rotation that races a send (covered by the existing
lock and by `getMySenderKey` re-selecting); chatty bot groups rotate often (N is per key, tune it); the server's KDM rate limits must
allow the burst when all devices cross the age threshold together (add jitter).

### 8.2 Receive-side epoch cut-off

**What.** Refuse (or mark) a message whose key epoch is older than the epoch in which it was posted.

**Why it is weaker than it looks.** The epoch change time and the group membership come from the **server**: a hostile server can
simply lie about them, so a cut-off only helps against a server that is honest but buggy, or an attacker who can post but not edit the
server's records. The signature already makes such a message attributable to its true author (7.7 item 2).

**Risks.** Late delivery: a device that was offline, or an in-flight send during a rotation, legitimately sends under the previous
epoch; a hard reject would lose real messages. Multi-device skew: a device that has not yet rotated keeps sending under the old epoch for
a while. Clock and ordering assumptions between server time and message ids.

**Suggested shape if wanted.** Do not reject: accept within a grace of one epoch, and **mark** older messages ("sent from a
previous membership") so the user sees them as such; for a sender who is no longer a member show "former member". Put the epoch into the signed
bytes only if the receive rule needs it (the key id already commits to the epoch).

### 8.4 Safety numbers / key fingerprints (separate future item)

**Goal.** Close 7.7 item 3: let two people check that the identity public key each holds for the other is the one the other generated.

**Sketch.** (1) A fingerprint of the account identity public key (for example SHA-256 over a domain label and the key, shown as 12 groups of 5 digits and
as a QR code); (2) trust on first use: store each peer's key fingerprint locally when it is first seen and show a clear warning, not a silent
re-key, when it changes; (3) a "verified" mark after the user compares or scans, kept in local storage per peer; (4) for a group, a list of member
fingerprints in the members dialog, and a banner when a member's identity key changed since it was last seen. **Open points:** key change after a
legitimate device or password reset must not train users to ignore the warning; what a changed key does to DM history and to sending (block or warn); where the
trust store lives (it must survive logout but not be readable by the server); it needs product decisions and a UI, so it is a separate piece of work.
